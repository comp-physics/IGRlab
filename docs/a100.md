# Building and validating IGRlab on A100

Use the canonical `build.sh` driver. `--a100` selects native SM80 for dependencies,
MFEM, and application sources. `--gpu --cuda-arch 80` is equivalent. The HDG
runtime accepts native SM80 and SM120; its device check rejects a GPU that does
not match the configured architecture.

The SM120 route remains different: dependencies and application use SM120,
while MFEM generates `80-virtual`. Do not copy that MFEM setting into an A100
build. The driver validates both tuples and rejects the ambiguous `CUDA_ARCHS`
variable.

## Practical setup

Initialize the site's Spack shell support and use an SM80 dependency environment
with matching compiler, CUDA, MPI, HYPRE, Umpire, METIS, and BLAS/LAPACK identities.
The repository's `spack-envs/cuda-sm80` profile retains its pinned dependency
policy. An explicit site environment can be selected with `IGRLAB_SPACK_ENV`;
the legacy `DG_IGR_SPACK_ENV` override remains supported. Numerical-library
discovery uses exact installed prefixes, including explicit Spack externals.

The complete historical hardware validation used CUDA 13.0.1, GCC 12.3,
OpenMPI 4.1.8, HYPRE 3.1.0, Umpire 2025.12.0, and MFEM commit
`d9d6526cc1749980a2ba1da16e2c1ca1e07d82ec`. A separate
CUDA 12.9/HYPRE 2.32/Umpire 2024.07 fallback **compiled successfully**; that
fallback build is separate evidence from the CUDA 13 hardware tests.

Inspect the resolved paths and architecture before compilation:

```bash
./build.sh --a100 --hdg-runtime --print-plan
```

With dependencies installed, an iterative host compilation can use:

```bash
./build.sh --a100 --hdg-runtime --no-clean --no-deps --no-tests -j 2
```

The `-j 2` setting reflects the campaign's compiler memory experience; eight
simultaneous jobs exhausted a 24 GiB allocation. Choose jobs for the actual
host. Omit `--no-deps` when the selected environment needs installation.
Use `--reuse-mfem-root DIR` only for a driver-admitted MFEM tuple or clean pinned
seed. The helper `build_mfem_tpl.sh` remains private.

Compilation with `--no-tests` does not execute numerical GPU tests. Run device
tests, MPI cases, and profiling only on authorized resources with exclusive GPU
access. An output lock protects build directories; it does not reserve a GPU.
Use the driver's `--test-regex` to select required validation and
`--nvtx-profile` for profiler binaries.

## Output paths and environment compatibility

The default output root is `${XDG_CACHE_HOME:-$HOME/.cache}/igrlab-build`.
Resolution is `--output-root`, then nonempty `IGRLAB_OUTPUT_ROOT`, then legacy
`DG_IGR_OUTPUT_ROOT`, then that default. Existing outputs can remain at their
original root:

```bash
./build.sh --a100 --hdg-runtime --no-clean --no-deps --no-tests \
  --output-root "${XDG_CACHE_HOME:-$HOME/.cache}/dg-igr-build" -j 2
```

Each checkout retains its own worktree/profile scope below the selected root.
A new checkout gets a new scope even when it shares the old output root; the
driver does not silently adopt another checkout's cache. Explicit MFEM reuse
still passes the existing identity checks. Identity schema names, fingerprints,
and stamp formats remain compatible with the previous code branding.

Nonempty canonical overrides take precedence over their legacy equivalents:

| IGRlab override | Legacy variable |
| --- | --- |
| `IGRLAB_OUTPUT_ROOT` | `DG_IGR_OUTPUT_ROOT` |
| `IGRLAB_SPACK_ENV` | `DG_IGR_SPACK_ENV` |
| `IGRLAB_CUDA_ARCH` | `SPACK_CUDA_ARCH` |
| `IGRLAB_MFEM_CUDA_ARCHS` | `MFEM_CUDA_ARCHS` |
| `IGRLAB_APP_CUDA_ARCHS` | `APP_CUDA_ARCHS` |
| `IGRLAB_BUILD_TYPE` | `CMAKE_BUILD_TYPE` |
| `IGRLAB_BUILD_JOBS` | `NPROC` |
| `IGRLAB_BUILD_RESEARCH_TESTS` | `DG_IGR_BUILD_RESEARCH_TESTS` |
| `IGRLAB_ACCELERATOR_KERNEL_SOURCES` | `DG_IGR_ACCELERATOR_KERNEL_SOURCES` |

Corresponding command-line options take precedence over environment values.
Empty canonical build overrides fall back to their legacy value or default;
this build-driver rule is separate from runtime environment handling.
Standard `TMPDIR` behavior is preserved. Existing command-line flags remain
valid.

Research-only tests and experiments are excluded from default builds. Opt in
with `--research-tests` or `IGRLAB_BUILD_RESEARCH_TESTS=ON`; the legacy
`DG_IGR_BUILD_RESEARCH_TESTS` name is accepted. Boolean values `ON/OFF`,
`TRUE/FALSE`, `YES/NO`, and `1/0` are accepted. `--no-research-tests` explicitly
disables this build selection. The plan records `research_tests`, and the
driver forwards the resolved selection to CMake. This controls target
selection independently of `--no-tests`, which controls CTest execution.

## Compiler and runtime fixes to preserve

The A100 port supports Umpire installations under `lib` or `lib64`, static
HYPRE/Umpire link ordering, concrete OpenBLAS identity, CMake 3.30 host-compiler
metadata, and HYPRE releases with or without the GMRES `precond_Mat` member.
The isolated DGSEM tensor benchmark implements TF32 ties-to-even conversion
without requiring an SM90-only conversion instruction.

The HDG application uses an opaque host facade. Engine construction, session
operations, and destruction stay in CUDA; the application wrapper compiles as
C++17. This avoids the observed CUDA 12.9/13 device-compiler crash while
preserving MFEM's CUDA-dependent object layouts.

The native trace solve uses immutable `__grid_constant__` launch records and
passes its preconditioner helper record by const reference. The annotation
alone failed the exact trace fixture. The combined implementation passed that
fixture and its memory check. Retain both changes.

The [p5/n16 HDG suite](../scripts/perf/suites/delta-hdg-p5-n16.json) is the
ordinary/tensor workload for subsequent high-order optimization. Delta A100 job
22916548 (2026-10-15) reused the accepted `60e3e74` executable and native test
binaries from build 22912505; no application or dependency rebuild was needed.
All three p5 high-order native checks passed: CPU/ordinary/tensor numerical
alignment and both CUDA engine lifecycle checks. They ran directly with
`--order 5 --high-order-smoke`; the new CTest registrations were not regenerated
in that retained build. The public active-IGR n16 two-step field comparison
passed at unchanged tolerances, with maximum absolute difference
`2.22e-15`, positive density/pressure, and nonzero sigma. Three unprofiled
ten-step runs at `dt=1e-5` gave median full-process times of **25.713 s ordinary**
and **4.983 s tensor**, including setup and shutdown. This is a workload-specific
engine comparison, not a measured source-change speedup or a convergence-order
study. See [GPU studies](gpu-studies.md) for broader validation limits.

The [DOF scaling suite](../scripts/perf/suites/delta-p5-dof-scaling.json)
keeps p5 and uses the same periodic unit-square mesh family. It includes a
common **589,824 conserved-state DOF** point for DG, DGSEM, ordinary HDG, and
tensor HDG, plus 147,456-DOF HDG and 2,359,296-DOF DG/DGSEM points. For these
uniform quadrilaterals the common count is `4 * elements * (p+1)^2`; general
hp meshes should use the actual conserved finite-element space's global true
size. HDG interior auxiliaries and global trace unknowns are separate counts,
not substitutes for the common physical-state denominator.
If adaptation changes the DOF count during a run, normalize accepted work by
the sum of the per-step DOF counts rather than the final count times the number
of steps. The current callback summary uses the final space size; the fixed
meshes in this calibration avoid that ambiguity.

Report full-process wall time both directly and divided by physical DOFs and
accepted steps. Also retain elapsed physical time, timestep, integrator, and
available accepted/rejected/RHS counts. The DG/DGSEM final callback uses the
conserved vector space's true DOFs, but its timer excludes initial setup and
includes final solver diagnostics. The current public HDG route has no
equivalent callback timer. Keep callback and full-process timing scopes
separate; the workload adapter's generic `seconds` observation currently uses
different scopes for DG and HDG. Lower time per DOF is a throughput result;
cross-order or cross-method time-to-solution claims additionally require a
common accuracy target. The existing mesh-dependent IGR alpha policy is
retained, so refinement changes the regularized workload.
